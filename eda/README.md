# 数据可视化环节（eda）— 按语料语言分两个子项目

数据侧有两套语料，可视化按语言拆成两个自成一体的子项目：

| 子目录 | 语料 | 上游清洗目录 | 小项目数 | 图片数 | 说明 |
|---|---|---|---|---|---|
| `en/` | 英文虚假职位（EMSCAD，简历式职位描述） | `data/data_process/` | 9（`eda01`~`eda09`） | 14 | 明细见 `en/README.md` |
| `zh/` | 中文招聘型电诈话术（352,836 行，10 类标签） | `data/zh_data_process/` | 10（`zh01`~`zh10`） | 26 | 明细见 `zh/README.md` |

每个子目录都自带 `config.py` + `eda_common.py` + 图脚本 + `figs/` + `csv/`，
**互不 import**，所以两个目录里有同名的 `config.py`——运行时靠"当前目录"区分（见下面的跑法）。

## 跑法

```bash
# 在仓库根目录执行
python -X utf8 eda/eda_all.py                 # 两个子项目依次跑完
cd eda/zh && python -X utf8 zh_all.py         # 只跑中文
cd eda/en && python -X utf8 en_all.py         # 只跑英文
```

依赖：matplotlib、seaborn、pandas、numpy、wordcloud（中文词云另需中文字体）。
数据路径由各子项目的 `config.py` 统一推导到仓库根下的 `data/zh_data_process/` 与 `data/data_process/`，
不依赖运行目录；`figs/` 里的图片是原环境生成后一并入库的，重跑脚本会覆盖同名文件。

- `PYTHONNOUSERSITE=1` 必须加，否则用户站点里的 numpy 会和 Anaconda 的 pandas 串版本直接报错。
- 单独跑一个小项目：进对应目录 `python -X utf8 zh07_keyword_lift.py`。
- 产物：各子目录的 `figs/*.png`（答辩PPT直接插）+ `csv/*.csv`（图背后的数字，被追问时查）。
  zh 侧全量跑一遍约十几分钟，主要时间在 35 万行上跑正则和字符 n-gram。

## 每张图都有中文标题，靠的是三处设置

1. `eda_common.py` 里 `plt.rcParams["font.sans-serif"] = ["Microsoft YaHei","SimHei","DejaVu Sans"]`
   + `axes.unicode_minus=False` —— 标题、坐标轴、图例、刻度、表头全走这里。
2. `config.py` 里的映射表（`split_name_map` / `length_name_map` 两侧都有，
   `label_name_map` 在 en、`group_kind_name_map` 和 `safe/fraud_binary_name` 在 zh）
   —— 中英文对照只在这里写一次，脚本里只引用列名，改文案不用动图脚本。
   中文侧 10 类名不进映射表，直接从 `class.txt` 按行号取，避免和上游不同步。
3. 词云本体例外：WordCloud 不走 matplotlib 的字体，必须单独给
   `font_path=C:\Windows\Fonts\msyh.ttc`（见 `zh/config.py`），漏了词云里的中文全是方框。

**故意保留原文的三类**：① 关键词本身（petroleum、向指定…），翻了没法回语料核对；
② 文本预览（那是数据原文）；③ 文件名和 `class.txt` 里的标签值（跨脚本口径，只在图上显示中文）。

## 两个子项目放一起看的四条主结论

1. **失衡方向相反，而且中文侧的量级变了**：英文侧欺诈 4.81%（少数类），
   中文侧塌回二分类后诈骗 60.66%（多数类；旧版是 75.62%，这个数字已经作废）。
   中文侧真正的不均衡在 **10 类之间**：最大类 24.28%、最小类 0.60%，差 40 倍。
   所以"类别不均衡"这句话在两侧含义完全不同，答辩要分开讲。
2. **投满分的 `pad_size=32` 两侧都不能用**：截到 32 个单位，英文盖住约 5%（词），
   中文只剩 **0.25%**（字）——中文侧比旧数据的 0.60% 更不能用。
   要 324 词（英文 P90）/ 268 字（中文 P90）才盖住 90%，
   512 才两边都过 98%（英文 98.08%、中文 99.77%）。
   注意 512 是 BERT 的位置上限，fastText 没有这个约束，别说成"模型都必须 512"。
3. **两侧都有"背模板"的风险，但性质不同**：
   英文 train 内部逐字重复 22.87%（涉及 4,521 行），dev/test 为 0；
   中文三份切分内部逐字重复 0、跨切分 0，但抹掉数字/网址/【】做骨架归一后，
   **仍有 88 个模板家族跨切分（占 0.0249%）**，最大家族 17 条横跨 3 个切分。
   → 中文文档里"重复率 0%"这句要加限定：**逐字重复为 0，模板级近重复不为 0**。
4. **`group` 这一列在两侧完全不是一回事，处理方式不能照搬**：
   英文侧 group = MinHash 近重复组，组内标签冲突就整组剔除（只丢 5 组 34 条）；
   中文侧 group = 案件级溯源，40,496 个多行组里 **95.9% 天生含 ≥2 个类别**
   （一个案件既有诈骗句也有无风险句），照搬英文规则要扔掉 100,507 条 = 28.49% 的数据。
   两侧跨切分的组数实测都是 0 → 泄漏是靠切分方式消除的，不是事后删数据。
